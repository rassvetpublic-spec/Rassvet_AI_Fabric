# Скилл безопасного удаления чата (/del)

Этот скилл запускается по команде `/del` в **любом репозитории флота или изолированном проекте**. Он гарантирует, что ни одна строчка ценного кода, гипотеза, архитектурная идея или предложенная задача не пропадет при удалении окна чата.

## Алгоритм работы (Строгий порядок)

### Шаг 1. Первичный аудит и обновление каталогов
1. **Обновить каталоги скриптов (если применимо)**:
   - Если в текущем проекте есть `scripts/generate_catalog.py`, запустить `python scripts/generate_catalog.py`.
   - Если есть тесты или самодиагностика (`tools/tower_self_audit.py`, `tools/verify_fleet_mcp_clients.py`), проверить чистоту контура.
2. Внимательно проанализировать всю историю текущего чата (transcript) снизу вверх.
3. Найти все фрагменты кода, "супер-идеи", решения и задачи, которые еще не были сохранены на диск, не отправлены в Issue или не опечатаны.

### Шаг 2. Автоматическое сохранение невыполненных предложений (No Dropped Proposals)
1. Выделить все не вошедшие в текущую сессию рекомендации горизонта `[Класс A/B/C - X/Y/Z]`.
2. Если доступен инструмент `tools/proposals_preserver.py` (в `CONTROL_TOWER`), вызвать его для автоматической регистрации GitHub Issues в целевых репозиториях и записи в `telemetry/unaccepted_proposals.json`.
3. Если инструмент недоступен — зарегистрировать открытые предложения через `gh issue create` в репозитории текущего проекта или зафиксировать их прямо в отчёте удаления.
4. При наличии других неструктурированных идей задать уточнение через `ask_question`.

### Шаг 3. Вторичная верификация и статус Git
1. Проверить `git status` текущего проекта. Все готовые изменения должны быть закоммичены либо явно учтены.
2. Проверить статус сопряжённых репозиториев, если в чате велась сквозная работа.
3. Рассчитать метрику потерь (Loss Threshold): процент ценной информации, которая исчезнет при удалении чата (целевой показатель: 0.0%).

### Шаг 4. Универсальное сохранение отчёта (Чат + Внешний файл)
Финальный дайджест **ОБЯЗАТЕЛЬНО выводится в чат**, а его копия сохраняется во внешний файл на диске.

**Динамическое определение пути сохранения отчёта:**
Агент определяет корень текущего проекта (`<REPO_ROOT>`) и выбирает каталог по приоритету:
1. `<REPO_ROOT>/docs/history/delete_audit_<session_id>.md` (стандарт документации)
2. `<REPO_ROOT>/История/delete_audit_<session_id>.md` (русскоязычный канон)
3. `<REPO_ROOT>/checkpoints/delete_audit_<session_id>.md` (канон Башни)
4. `<REPO_ROOT>/.agents/history/delete_audit_<session_id>.md` (системный канон)
5. Если ни одна из директорий не существует, агент создает `<REPO_ROOT>/docs/history/`.

**Структура отчёта:**
1. **Дайджест сохранения**: Таблица с абсолютными путями к изменённым файлам и ссылками на коммиты/PR/Issues.
2. **Список потерь**: Перечисление удаляемых данных (только эфемерные логи UI и отладочный вывод).
3. **Визуализация сохранности**:
   `Сохранность контекста: [████████████████████] 100% (Потери: 0.0%)`
4. **Финальная плашка**:
   > [!TIP]
   > **Удаляй этот чат — безопасно сохранено в:**
   > - <перечисление локальных файлов и ссылок на Issues>
