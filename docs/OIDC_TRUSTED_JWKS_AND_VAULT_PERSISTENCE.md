# Этап 09.5 — доверенные OIDC-ключи и защищённая запись на Windows

**Статус:** реализация готова к контрольной Windows-проверке. **Язык:** русский. **Внешние запросы:** в тестах отсутствуют.

## 1. Доверенные ключи

Модуль `rai_fabric.trusted_jwks.TrustedOpenAIKeys` получает OIDC Discovery **только** с `https://auth.openai.com/.well-known/openid-configuration`. Поле `issuer` обязано совпасть с `https://auth.openai.com`, а `jwks_uri` — с документированным `https://auth.openai.com/.well-known/jwks.json`. Используются системные CA для HTTPS, ограничение времени, запрет HTTP-redirect и прокси, лимиты длины и строгая обработка JSON. Содержимое JWT не выбирает URL ключей.

Допустимы только публичные RSA-ключи подписи `RS256`, неповторяющиеся идентификаторы `kid`; приватные параметры JWKS отклоняются. Верификация токена остаётся в `oauth_identity.verify_id_token`, проверяющем подпись, `iss`, `aud`, `nonce`, `exp`, `iat`, `sub`, `azp`.

Кеш JWKS — только в памяти процесса, стандартный TTL 600 секунд. Просроченный кеш не считается доверенным; при неизвестном `kid` разрешено ограниченное повторное обновление (интервал 30 секунд). Сетевой вызов выполняется **только по явному запросу**, никогда при импорте модуля. В CI используются исключительно подставные ответы и синтетические RSA-ключи.

## 2. Хранение в Windows

Новый публичный интерфейс `WindowsCredentialVault` доступен **только на Windows**. Он использует ранее проверенный `WindowsUserDPAPI`, без `LOCAL_MACHINE`, и выделенный каталог `%LOCALAPPDATA%\Rassvet_AI_Fabric\oauth_v1`. При первой записи каталог создаётся с защищённой DACL одного текущего SID. Для каталога, временного и окончательного файла ACL читается обратно и проверяется: отсутствие наследования, единственный разрешающий ACE пользователя и полный доступ только этого SID. Любая ошибка — отказ, не автоматическое ослабление ACL.

Для OAuth-записи используется обезличенное имя по SHA-256 от `(issuer, client_id, subject)`. Весь комплект `access_token` / `refresh_token` / `id_token` и метаданных хранится **одним DPAPI-зашифрованным документом**. `save(identity, record)` создаёт запись, а `save(identity, next_record, expected_revision=old_revision)` меняет её только при точном совпадении ревизии. Блокировка `.lock` не позволяет двум процессам обновлять один refresh-токен одновременно. Старые зашифрованные байты не уничтожаются до успешной записи, `fsync` и `os.replace`. После сбоя с оставленной блокировкой требуется ручная проверка; устаревшая блокировка автоматически не удаляется.

Проверяются символические ссылки и junction в родительских каталогах и файлах. Режимы тестов на Windows используют отдельную временную папку `oauth_v1_test_<uuid>` под каталогом приложения и **только фальшивые токены**. Код не получает реальную авторизацию и не выполняет запросы к модели.

### Ограничения безопасности

- DPAPI текущего пользователя и NTFS DACL не защищают от вредоносного процесса, работающего с тем же SID, от администраторов или от компрометации Windows.
- Проверка путей по именам не устраняет полностью гонки TOCTOU при активном локальном злоумышленнике. Для удалённого недоверенного многопользовательского запуска нужен отдельный аудит и работа с дескрипторами файлов.
- `os.replace` даёт атомарную замену файла в одном томе, но не гарантирует восстановление при аппаратном отказе носителя в любой момент.
- Python не гарантирует стирание всех копий plaintext в памяти. Запрещено логировать объект с полями токенов или передавать его в checkpoint.
- Используется только `urn:uuid:<UUIDv4>` для host ID в этой версии. Другие официально допустимые форматы требуют отдельной реализации и тестов.
- Проверка ID-токена **не даёт** разрешения использовать подписную модель. После живого OAuth следует отдельно подтвердить полученные scopes, включая `chatgpt.tokens.use.direct`, и фактическую доступность подписки.
- В этой реализации **нет** OAuth code exchange, автоматического token refresh или реальных вызовов Responses API. В рабочий контроллер vault пока не подключён.

## 3. Ограничения GitHub Actions

Проект целиком ориентирован на Windows. CI использует **только Windows**, одну Python 3.11 на обычный кодовый push. Linux/macOS jobs, повторные проверки ради документации, постоянные автоповторы и платные API не допускаются. Для этапа 09.5 сначала выполняются локальные тесты, затем **один контрольный Windows CI** на готовом исходном коммите. Изменения только документов/checkpoint не должны запускать workflow.

## 4. Критерии приёмки

1. Синтетические OIDC/JWKS, TTL, замена `kid`, недоверенные URL и отказ сети — PASS.
2. Тесты CAS-замены refresh-токена, crash до `os.replace`, блокировки и reparse — PASS.
3. Windows: реальные DPAPI + DACL readback, создание/чтение/замена, отказ на посторонний путь — PASS.
4. Полный набор тестов для точного коммита в Windows CI — PASS.
5. `CODEX_HOME`, BPR40, CONTROL TOWER и существующие профили авторизации не изменены.

После пункта 4 допустим курсор `RAI-FABRIC/09.6-LIVE_OAUTH_CONSENT_GATE`, но только для **отдельно разрешённого** интерактивного входа владельца.
