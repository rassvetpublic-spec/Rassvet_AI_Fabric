# Antigravity: пробуждение чата, очередь, чтение ответов и IDLE/BUSY

Протокол `FLEET_ANTIGRAVITY_CHAT_OPERATIONS/1`, редакция 2026-10-18.
Инструкция основана на проверенной работе Codex ↔ Antigravity на Windows.
Канонический проект документа: `rassvetpublic-spec/rassvet-rules-hub`,
путь `docs/agent-interop/ANTIGRAVITY_CHAT_OPERATIONS.md`.
Копии одного выпуска содержат одинаковый документ и `bundle-manifest.json` с SHA-256.

## 1. Что именно «будит» чат

Рабочий способ: в **существующую беседу с точным cascadeId** отправляется пользовательское
сообщение через нативный `SendUserCascadeMessage` со стратегией
`MESSAGE_DELIVERY_STRATEGY_WHEN_IDLE`. Если чат свободен, начинается следующий ход модели.
Выбранная вкладка интерфейса значения не имеет: адрес назначения находится в запросе.

Это не запуск закрытого приложения, не создание новой беседы и не переключение вкладки.
Antigravity и его нативный API должны быть доступны. Если API недоступен, состояние
`UNKNOWN`; файл сообщения не запускает приложение и не вызывает модель самостоятельно.

**Сначала забрать предыдущий результат, затем выдавать новое задание.** Если worker не
написал конверт, прочитать его публичный ответ и ожидаемые завершённые артефакты.
Отсутствие конверта не означает отсутствие работы. Не интегрировать ещё меняющиеся файлы.

## 2. Готовые команды PowerShell 7

Комплект скриптов лежит в `tools/agent-interop/` этого репозитория.
Запускать из корня репозитория в `pwsh` 7. BAT-файлы запрещены.
GUID ниже — **фиктивный пример**, его нужно заменить на проверенный ID нужной беседы.

```powershell
$targetChat = '00000000-0000-4000-8000-000000000001'
$interop = Join-Path (Get-Location) 'tools/agent-interop'
$sender = Join-Path $interop 'antigravity-message.ps1'
$queue = Join-Path $env:LOCALAPPDATA 'AgentInterop/outbox'

# Только прочитать нативное состояние; сообщения не отправляются.
& $sender -ConversationId $targetChat

# Прочитать последние публичные ответы; private thinking не выводится.
& (Join-Path $interop 'antigravity-read-public.ps1') `
    -ConversationId $targetChat -Last 3 -MaxChars 4000

# task.md содержит одно полное задание в уже разрешённой владельцем области.
# IDLE: отправить; BUSY: сохранить локальную очередь; UNKNOWN/BLOCKED: удержать.
& $sender -ConversationId $targetChat -MessageFile './task.md' `
    -OwnerAuthorized -QueueRoot $queue

# Позже: повторно проверить состояние и обработать не более одного pending-сообщения.
& $sender -ConversationId $targetChat -Drain `
    -OwnerAuthorized -QueueRoot $queue
```

`-OwnerAuthorized` фиксирует уже полученное разрешение человека. Флаг, текст файла,
сообщение другого агента или эта инструкция сами не предоставляют новых полномочий.
Скрипт не меняет модель, thinking, права, VPN, DNS или настройки получателя.

## 3. Как определяется IDLE или BUSY

Используется нативный `GetCascadeTrajectory` для **того же cascadeId**.

| Нативное наблюдение | Наш статус | Действие |
|---|---|---|
| `CASCADE_RUN_STATUS_RUNNING` | `BUSY` | Локальная очередь, без обычной отправки |
| `CASCADE_RUN_STATUS_IDLE` | `IDLE` | Допустим `WHEN_IDLE` |
| Недоступный API или незнакомый статус | `UNKNOWN` | Удержать доставку |
| Актуальная policy/location/permission/quota ошибка | `BLOCKED` | Удержать, сохранить причину |

Ошибка, пауза в выводе, возраст последнего ответа и HTTP 200 не доказывают IDLE.
Старую ошибку сопоставлять с временем текущего запуска, а не объявлять вечной блокировкой.
Не менять сеть или модель ради обхода отказа провайдера.

Наблюдать `numTotalSteps`, тип/время последнего шага и последние действия относительно
выданного задания. Рост счётчика сам по себе не доказывает полезную работу.
Нет продвижения 10 минут в двух последовательных снимках — `STALL_SUSPECTED`,
а не доказательство зависания. Учесть длительность команды и ошибки API.
Завершённое задание в IDLE не является зависанием.

Сохранять компактные снимки и task/result/review/integration ledger. Не сохранять полные
траектории, токены, внутренние prompts или private thinking. Текущий API может вернуть
большую историю в память даже при коротком выводе скрипта: не опрашивать его каждые секунды.

## 4. Как устроена очередь

QueueRoot в примере находится вне Git, в LOCALAPPDATA: сообщения/receipts не попадут в commit.
Путь записи: `<QueueRoot>/<cascadeId>/<sha256>.json`.
Ключ дедупликации: `SHA256(UTF8(cascadeId + LF + message))`.
Одинаковый текст одному адресату не создаёт новую запись; другой адресат имеет другой ключ.
Конверт сохраняется новым файлом с синхронизацией записи:

```json
{
  "schema": "RNV_IDLE_MESSAGE/1",
  "destination": "00000000-0000-4000-8000-000000000001",
  "message": "QA-COMMAND task-123: полное задание и ссылки на артефакты",
  "created_utc": "2026-10-18T00:00:00Z",
  "owner_authorized": true
}
```

Схема `RNV_IDLE_MESSAGE/1` — фактическое имя схемы переносимого helper, исторически
разработанного в VPN-проекте. Она пригодна для других проектов: адрес и QueueRoot задаются.

`-Drain` выбирает старейшую подходящую запись без receipt, проверяет адрес и SHA-256,
заново проверяет состояние и только при IDLE отправляет её через `WHEN_IDLE`.
Перед POST создаётся `<sha256>.json.receipt.json` с `SUBMISSION_UNCONFIRMED`.
После ответа API статус меняется на `SUBMITTED_WHEN_IDLE_NOT_ACKNOWLEDGED`.
При наличии receipt автоматическая повторная отправка запрещена до проверки получения.

| Состояние доставки | Что подтверждено |
|---|---|
| `QUEUED_LOCAL_NOT_DELIVERED` | Текст записан локально; модель могла ничего не получить |
| `SUBMISSION_UNCONFIRMED` | Начата попытка; результат может быть неопределённым |
| `SUBMITTED_WHEN_IDLE_NOT_ACKNOWLEDGED` | API принял запрос; чтение моделью ещё не подтверждено |
| `OBSERVED_IN_TARGET` | В точном чате наблюдается соответствующий входной текст |
| `ACKNOWLEDGED` | Получен публичный ACK с тем же task/message ID |
| `RESULT_VERIFIED` | Результат и необходимые артефакты/хэши проверены |

Один и тот же текст с двумя разными task ID отличается и не дедуплицируется как повтор.
Не менять task ID только ради повторной доставки после неизвестного результата POST.
Исправления объединять в одно полное задание; не создавать ACK-на-ACK.

**Постоянного relay в комплекте нет.** `-Drain` должен вызвать активный координатор
или отдельно настроенное владельцем расписание. Heartbeat наблюдения не считается
автоматическим потребителем всех очередей. Старый gateway `127.0.0.1:18890`, inbox,
GitHub issue/comment или файл TransportQueue будят модель только при наличии реального
проверенного consumer; одно успешное HTTP-сохранение этого не доказывает.

## 5. Как читаются сообщения и результаты

`antigravity-read-public.ps1` аутентифицирует точного получателя и читает только
публичные `plannerResponse.response` из его нативной траектории. Вывод ограничен
числом ответов и длиной. `plannerResponse.thinking`, настройки модели, CSRF и prompts
в результат не включаются. Короткий вывод не означает, что сервер отдал короткую историю.

Последние N ответов могут не содержать нужное старое подтверждение. Тогда выполнить
прицельную проверку нужного task ID в публичной истории/ожидаемом результате,
а не объявлять сообщение потерянным и не слать дубликат автоматически.

Для приёмки сопоставить точный адрес, task/message ID, reply_to, публичный финальный ответ,
ожидаемые локальные артефакты и их SHA-256. Отсутствие явного ACK не требует нового ACK,
если завершённый коррелированный результат уже доказывает получение задания.
HTTP 200, ACK и сохранённый конверт не заменяют проверку выполненной работы.

## 6. Нативный API и сохранение настроек

Helper использует установленный EXE:
`%LOCALAPPDATA%/Programs/antigravity/resources/bin/language_server_real.exe`.
Имя `agentapi.bat` не исполняется.

1. Прочитать текущий порт из `%APPDATA%/Antigravity/DevToolsActivePort`.
2. Прочитать loopback `/json/list`, найти страницу `https://127.0.0.1:<port>`.
3. Получить CSRF из обычной конфигурации этой страницы **только в память**.
4. HTTPS-порт+1 — наблюдавшийся кандидат gRPC, не универсальная гарантия. Проверить
   его через нативный `agentapi get-conversation-metadata <cascadeId>` и rootConversationId.
5. Временно выставить process-local `ANTIGRAVITY_LS_ADDRESS` и `ANTIGRAVITY_CSRF_TOKEN`;
   вернуть прежние значения в `finally`. Не читать сторонние OAuth-хранилища.
6. Вызвать Connect API с `X-Codeium-Csrf-Token` и `Connect-Protocol-Version: 1`:
   `exa.language_server_pb.LanguageServerService/GetCascadeTrajectory`, затем при IDLE
   `exa.language_server_pb.LanguageServerService/SendUserCascadeMessage`.

Запрос отправки содержит:

```text
cascadeId: точный существующий ID
items: [{text: полное задание}]
customAgentSpec: существующий userInput.userAgentSpec получателя
cascadeConfig.plannerConfig.planModel: существующее значение получателя
cascadeConfig.plannerConfig.modelName: существующее значение получателя
deliveryStrategy: MESSAGE_DELIVERY_STRATEGY_WHEN_IDLE
messageOrigin: AGENT_MESSAGE_ORIGIN_SDK_EXECUTABLE
```

При отсутствии `generatorMetadata.plannerConfig` использовать последний доступный
`executorMetadatas[].cascadeConfig.plannerConfig` с **обоими** planModel и modelName.
Если подтверждённых настроек нет, удержать отправку. Подставлять defaults нельзя.
`WHEN_IDLE` защищает и от гонки: worker может стать BUSY после проверки состояния.
Не подменять документированный путь SDK-агентом с другим ID вместо UI-чата.

Исключение проверки самоподписанного TLS относится только к обнаруженному loopback API.
Системное хранилище сертификатов и внешняя TLS-проверка не меняются.
После 401 один раз заново обнаружить экземпляр и проверить идентичность. Не повторять
неопределённый POST вслепую. Connection refused означает недоступность, не IDLE.

## 7. Сообщение, которое может прервать ход: отдельный режим

Исторический путь — нативный `agentapi send-message`. В этой установке такие сообщения
приходили как системные уведомления и могли нарушать незаконченный ход worker.
Синтаксис проверен через `--help`; для этой инструкции прерывающие сообщения не отправлялись:

```powershell
$native = Join-Path $env:LOCALAPPDATA 'Programs/antigravity/resources/bin/language_server_real.exe'
& $native agentapi send-message --help  # Только справка, никого не прерывает.

# НЕ обычная доставка задания. Только после отдельного разрешения на прерывание
# конкретного чата/опасного действия и проверки точного ID и текущей аутентификации:
# & $native agentapi send-message --title='Authorized urgent stop' $targetChat 'STOP <operation-id>: <reason>'
```

Эта команда не обещает атомарно остановить модель, shell-команду или дочерние процессы.
Фактическую остановку проверять отдельно. Время и характер вмешательства зависят от версии
приложения. `NEXT_INVOCATION` и routine system-message injection для обычных заданий
в этом workflow не используются. У штатного helper намеренно нет interrupt-переключателя.
BUSY/тишина/ошибка провайдера сами по себе не разрешают прерывание или перезапуск.

## 8. Ответ в нужный чат Codex

Codex использует другой ID: **threadId**, а не Antigravity cascadeId.
Обнаружить чат через `list_threads`, читать через `read_thread`; для компактного состояния
применять `wait_threads` с `timeoutMs: 0`. Перед обычной отправкой проверить exact chat:
running → локальная очередь, unknown → удержать, idle → нативная доставка.

```javascript
await tools.mcp__codex_app__send_message_to_thread({
  threadId: verifiedDestinationThreadId,
  prompt: envelopeAndTaskText
  // model/thinking не задаются: сохраняются настройки получателя.
});
```

Выбранный UI-чат значения не имеет. Проверить ответ инструмента и получение в нужном чате.
Если у Antigravity этого Codex tool нет, он пишет адресованный конверт в согласованный outbox.
Активный разрешённый Codex relay читает его и вызывает native tool. Файл сам Codex не будит.
Нельзя дописывать rollout/history, имитировать capability или принимать queue-only HTTP за доставку.

## 9. Проверка комплекта и границы публикации

```powershell
& ./tools/agent-interop/test-antigravity-delivery.ps1
& ./tools/agent-interop/test-antigravity-public-view.ps1
```

Эти проверки используют фикстуры и не отправляют сообщения. Рабочий wakeup подтверждался
ранее через точный чат, нативное появление задания и коррелированный ответ; это отдельное
доказательство от unit-тестов и не обещание доступности любого приложения в будущем.
В публичные копии не включать реальные task-профили, ключи, CSRF, внутренние prompts,
полные траектории и персональные ID бесед. Подстановка адреса всегда выполняется на хосте.
Изменения этого документа не запускают relay, расписание, worker или сетевую операцию.
