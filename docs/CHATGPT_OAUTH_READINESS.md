# Готовность к авторизации ChatGPT по подписке — 09.3

**Статус:** подготовка OAuth/PKCE испытана офлайн. Реальная авторизация и доступ к моделям **не испытаны**. Официальный язык: русский.

## Назначение

`src/rai_fabric/oauth_readiness.py` готовит одну изолированную попытку входа по официальной схеме **Sign in with ChatGPT**. Это собственный код Rassvet AI Fabric, независимый от реализации донорских проектов.

1. Используется `https://auth.openai.com/api/accounts/authorize`, первый запуск с `client_id=dynamic_agent_client`, уникальным `ext_agent_host_id` и именем `rassvet_ai_fabric`. После успешной регистрации требуется сохранить полученный настоящий `client_id`; `dynamic_agent_client` — лишь точка входа.
2. Генерируются криптографически случайные `state`, `nonce`, PKCE verifier и challenge `S256`. Callback ограничен точным URI `http://127.0.0.1:<порт>/auth/callback`. Использование `localhost` или другого пути не допускается.
3. Ответ браузера проверяется на корректность URI, совпадение `state`, отсутствие повторяющихся полей, отсутствие ошибки, наличие кода и правдоподобного зарегистрированного `client_id`. Одноразовый шлюз `OAuthCallbackGuard` запрещает повторную приёмку.
4. Результаты проверок **не содержат** код, verifier, nonce или state. Пока не произошли обмен кода и **проверка криптографической подписи ID-токена**, доступ к подписке считается неподтверждённым.
5. Scopes запрашиваются: `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`. Право на рассуждение по подписке необходимо проверить именно по scopes ответа token endpoint и верифицированной личности; запросить scope недостаточно.

## Что принципиально не реализовано

- Открытие браузера, локальный callback HTTP-listener, реальный обмен кода, refresh tokens.
- Подпись ID-токена через JWKS, проверка `iss`, `aud`, `exp`, `nonce`, `sub`, сохранение identity.
- Шифрование учётных данных через Windows DPAPI и контроль доступов файлов.
- Запуск Codex App Server с пользовательским OAuth-токеном, реальный запрос `/v1/responses` и проверка доступной квоты.
- Автоматическое разрешение действий worker, платный API fallback, доступ к `.codex/auth.json` или браузерным cookie.

Все перечисленные операции требуют отдельных реализаций, тестов и согласия владельца для настоящей авторизации. Реализация шлюза не должна когда-либо писать в логи `callback_url`, `authorization_url`, HTTP-заголовки токена или полную переменную окружения процесса.

## Отдельные инварианты безопасности

- Вход одного аккаунта не может перезаписать уже активную авторизацию другого аккаунта до полной проверки идентичности и scopes.
- При отказе/ошибке/перезагрузке невыполненный вход заканчивается `BLOCKED`; нельзя автоматически повторно обменивать одноразовый код.
- Динамически полученный `client_id` должен сопоставляться с верифицированным `sub` и стабильным `ext_agent_host_id`.
- JWT-нельзя доверять после простого Base64-декодирования. Для валидации подписи применять поддерживаемую криптографическую библиотеку и официальные ключи OpenAI, а не собственную реализацию RSA.
- Windows CI проверяет только офлайн-логику: не читает ChatGPT credentials и не отправляет запрос модели.
